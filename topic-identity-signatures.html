Topic 6 — Sender Identity & Signatures

What does the recipient actually see — the collective identity, the person behind it, or a mix of both? And can the team enforce a consistent signature?

Comparison of sender identity and signatures across the 7 options

Branding vs accountability trade-off

The shared account (1) gives the cleanest external identity but zero internal accountability. Delegation (2) is the pragmatic middle ground: with the delegation sender display set to "account owner only", recipients see a pure collective identity, while audit logs still record which delegate acted — accountability stays internal, branding stays clean. For a nonprofit answering to donors and partners, a consistent signature also signals professionalism: only mailbox-based options (1, 2) enforce it.

User perspective

  • From-dropdown discipline. With options 4–6, selecting the right From address on every message is manual. One setting mitigates this for replies: Settings → Accounts and Import → Send mail as → "When replying to a message" → "Reply from the same address the message was sent to". New outgoing messages still require a manual choice each time.
  • Signature maintenance. Gmail does support one signature per sendAs address (chosen from the dropdown above the signature editor), so the official text can be attached to the shared identity specifically — but with options 4–6 each member must still create it and keep it up to date by hand. In practice, signatures diverge within months.
  • Display-name drift. The recipient-visible name is part of each member's own sendAs configuration, so the same address can appear as "Support — John" on one reply and "Support Team" on another. The API push described below can standardize the display name together with the signature.
  • Mobile divergence. The Gmail mobile app has a single per-account "Mobile signature" that applies to everything sent from the app, whatever From address is selected; if left empty, new messages fall back to the web signature. There is no per-From-address signature in the app, so phone replies can silently break the standardized signature.

Administrator perspective

Web console

Mail delegation sender display (Admin console → Apps → Google Workspace → Gmail → User settings → Mail delegation) offers two choices: Show the account owner and the delegate who sent the email or Show the account owner only. With Allow users to customize this setting checked, each account owner can override the choice in their own Gmail settings; unchecked, the admin value applies to the whole organizational unit.

Gmail append footer (Admin console → Gmail → Compliance) can append a legal footer tenant-wide or per organizational unit, but it is added at transport time — invisible while composing — and it cannot manage per-user signatures or From selection. With options 4–6, an OU-wide footer also stamps members' personal mail. No console setting enforces signature content.

API & automation

Signatures are scriptable: the Gmail API (users.settings.sendAs, signature and displayName fields) can push a standardized signature and display name to every member's sendAs identity — with domain-wide delegation this is a realistic scheduled task. Details in Topic 10 — API & Automation.
