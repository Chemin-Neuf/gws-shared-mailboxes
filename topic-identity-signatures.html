Topic 6 — Sender Identity & Signatures

What does the recipient actually see — the collective identity, the person behind it, or a mix of both? And can the team enforce a consistent signature?

Comparison of sender identity and signatures across the 7 options

Option From: Address Seen by Recipient "On Behalf Of" Disclosure Shared Signature Enforcement Key Caveats
1. Shared Password Account The shared address, indistinguishable from a personal account. None perfectly transparent Yes one account = one signature Perfect identity illusion — which is precisely the accountability problem.
2. Gmail Delegation Account The shared address. Yes depending on client, "sent by delegate@…" may appear in headers; Gmail shows the delegate in the web UI Yes signature belongs to the shared account, applies to all delegates Headers reveal the acting delegate — good for audit, visible to technical recipients.
3. Collaborative Inbox The group address (when replying via the group). Partial Groups UI shows the author; mail headers may show member address No no shared signature concept in Groups Replies via "Send Mail As" fall back to option 6 behavior.
4. Distribution List + Send As The list address, if the member selects it in the From dropdown. Possible unverified sendAs may show "via" in some clients No each member manages their own signature Identity consistency depends on every member's discipline.
5. Email Alias + Send As The alias address. Possible same "via" caveat N/A single user Simple and clean for one-person ownership.
6. "Send Mail As" Config Whichever address is selected in From. Possible No per-user signatures A wrong From selection sends personal mail as the team — or the reverse.
7. Email-to-Google Chat Space N/A no native external reply from Chat N/A N/A External replies are sent from Gmail and inherit that option's behavior.

Branding vs accountability trade-off

The shared account (1) gives the cleanest external identity but zero internal accountability. Delegation (2) is the pragmatic middle ground: recipients see the collective identity, while audit logs — and message headers — still record which delegate acted. For a nonprofit answering to donors and partners, a consistent signature also signals professionalism: only mailbox-based options (1, 2) enforce it.

User perspective

  • From-dropdown discipline. With options 4–6, selecting the right From address on every message is manual. Gmail does remember the last choice per conversation, which mitigates but does not eliminate errors.
  • Signature maintenance. Members of a distribution list must each paste the official signature into their personal settings — and update it whenever it changes. In practice, signatures diverge within months.

Administrator perspective

Web console

Gmail append footer (Admin console → Gmail → Compliance) can append a legal footer tenant-wide, but it cannot manage per-user signatures or From selection. No console setting enforces signature content.

API & automation

Signatures are scriptable: the Gmail API (users.settings.sendAs, signature field) can push a standardized signature to every member's sendAs identity — with domain-wide delegation this is a realistic scheduled task. Details in Topic 10 — API & Automation.
