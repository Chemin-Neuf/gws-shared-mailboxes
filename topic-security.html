Policy directive: shared passwords are never acceptable

Option 1 fails every row of this table. Beyond the technical lockouts, shared credentials void individual accountability — unacceptable for an organization handling donor data and subject to GDPR-style obligations. Where a "shared account feel" is truly required, Delegation (option 2) delivers the same UX without sharing any secret. See the synthèse managériale for the governance wording. One narrow, consciously risk-accepted exception is examined below — a bounded deviation, not a relaxation of this rule.

Niche pattern: federated SSO accounts for short-term external users

Scenario: a shared address that many external, short-term people must use — seasonal volunteers, event teams, partner staff. The delegation route means creating a licensed personal account per person, granting delegation, then deprovisioning a few weeks later. That churn costs one license per person and pushes the tenant toward the 2,000-user Nonprofits cap for accounts that sit idle most of the year.

A verified-feasible variant keeps one account per shared address, placed in a dedicated OU whose SSO profile points to a third-party SAML IdP operated by IT.1 Password and MFA policy then live entirely at the IdP; the credential is held in the password manager and can be rotated and redistributed by script. External users never see a Google password prompt: after entering the shared address on the Google sign-in page they are redirected to our IdP login.

What is verified on this edition

  • Per-OU SSO profiles are available on the Nonprofits edition. "Partial SSO" (assigning SSO profiles per OU or group) has been GA since 2021, and multiple third-party IdP profiles since 2022; both announcements explicitly list Nonprofits as eligible. The rest of the tenant keeps normal Google sign-in — only the dedicated OU authenticates against our IdP.1
  • MFA policy moves to the IdP — managed, not disabled. Google does not challenge SSO sign-ins with its own 2-Step Verification by default; Google-side 2SV and risk-based challenges for SSO users are opt-in.2 The 2FA-relay pain of option 1 therefore disappears. Recommendation: enforce MFA at the IdP with a centrally held factor rather than switching MFA off entirely — no MFA at all on a mailbox full of supporter correspondence would be the worst of both worlds.
  • Offboarding is fully scriptable. Rotate the IdP password, kill live Google sessions with one Admin SDK call (users.signOut; GAM equivalent gam user <address> signout), and push the new secret to the people who still need it via the password manager. Until rotation runs, a departed external keeps a working secret — rotation cadence is the revocation guarantee.3
  • License math: one license per shared address, zero per external person — instead of one license per person, with far less provisioning churn.

What this does not fix — read before adopting

  • Accountability stays void. Every action still maps to one shared identity; blocking criterion B7 in the decision guide excludes shared credentials by policy. This pattern is a bounded, consciously risk-accepted exception that needs explicit governance sign-off, restricted to addresses whose content can tolerate the accountability gap — never donor-sensitive correspondence.
  • The IdP becomes critical infrastructure. Its outage locks out every federated address at once; it must be patched, monitored, and backed up. Under the external-tools policy it requires a formal exception — a free self-hosted IdP (Keycloak, Authentik, etc.) fits the "free and limited-scope" criteria but is still one more system to operate.
  • Residual Google-side risk. One account used concurrently from many networks can still trip account-level protections (verification prompts, suspension for unusual activity). Super-admin accounts always keep Google password sign-in as break-glass access and are unaffected by the SSO profile.

Alternative that avoids the exception entirely

The same need is often covered without any shared secret: a Collaborative Inbox (option 3) with external members consumes no licenses — external people join the group with their own free consumer Google accounts, giving per-person attribution and instant revocation. The costs: each person needs some Google account, and the interface is the Groups web UI rather than a mailbox. When a true mailbox experience for externals is not mandatory, this is the cleaner answer; the federated pattern is for the cases where it is.

  1. Per-OU SSO profiles. "Assign SSO profile to organizational units or groups with the SAML Partial SSO feature" (Google Workspace Updates, 2021-11-19, GA) and "SSO profiles for multiple third-party identity providers" (2022-05-12); both list Google Workspace for Nonprofits among the eligible editions. Admin console path: Security → Settings → Set up single sign-on (SSO) with a third-party IdP → Manage SSO profile assignments. Checked 2026-09-14.
  2. Google 2SV and SSO. "Use Google 2-Step Verification and risk-based login challenges with 3rd-party identity providers" (Google Workspace Updates, 2019-09-26): both measures are opt-in for SSO organizations — by default a user authenticated by the IdP is not challenged again by Google.
  3. Session revocation. Admin SDK Directory API users.signOut (scope admin.directory.user.security) "signs a user out of all web and device sessions and resets their sign-in cookies" (developers.google.com, checked 2026-09-14). Changing the IdP password alone does not invalidate existing Google sessions — both steps are required.

Edition limits — Google Workspace for Nonprofits

  • No DLP (Data Loss Prevention) — rules scanning outbound mail for sensitive content require higher editions; not available on GWN regardless of the sharing option chosen.
  • No Google Vault — see Topic 5; retention is architectural, not policy-driven.
  • Available and usable: 2-Step Verification enforcement (free), security keys, context-aware access basics, Admin audit logs (login, admin actions, Groups audit, Gmail log search with limited retention), and alert center.

Administrator perspective

Web console

The Admin console covers: 2SV enforcement per OU, group membership and roles, delegation review (per user: Gmail settings; centrally: report), session revocation, and audit logs. Delegation grants can be inspected via the admin controls covered in Topic 9.

API & automation

Offboarding is highly scriptable: one GAM command chain can remove group memberships, revoke delegation grants, and revoke tokens for a departing user. Details in Topic 10 — API & Automation.
