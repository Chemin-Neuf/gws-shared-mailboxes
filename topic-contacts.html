Topic 7 — Contacts & Directory Access

When a team member writes from the shared identity, whose address book do they get? Personal contacts, the domain Directory, or the shared mailbox's own contact list? This is the topic most comparisons forget — and a real Google Workspace gap.

📅 Last updated: 2026-09-14 ✍️ Chemin Neuf Community · Kimi K3 🏷️ Status: Written

On this page

How contacts work in Google Workspace

Three distinct contact sources exist, and they are often confused:

  • Personal contacts — per-account, managed in contacts.google.com. A delegated or shared mailbox has its own personal contacts, separate from each delegate's.
  • Domain Directory — all users and groups of the tenant, plus admin-managed shared external contacts. Autocompletes for everyone when Directory is enabled.
  • Auto-collected "Other contacts" — addresses Gmail remembers from past correspondence, per account.

The structural gap: Google has no native "team address book" for arbitrary external contacts. Shared external contacts live in the Directory and are visible to the whole tenant — you cannot scope them to one team or one mailbox.

Admin-managed shared external contacts (Directory)

Administrators can add shared external contacts (Admin console → Directory → Directory settings, or the Admin SDK Directory API). These autocomplete for everyone in the tenant in Gmail, Contacts and mobile sync.

Limits relevant to a nonprofit

  • All-or-nothing visibility — no per-team or per-OU scoping of external contacts.
  • No user self-service — only admins (or API scripts) can add them; users cannot contribute.
  • Propagation delay — new shared contacts can take up to 24 h to appear in autocomplete.
  • Quota — the Directory accepts large volumes (hundreds of thousands of external contacts), far beyond nonprofit needs.

Delegated contacts — a building block across all options

Google Contacts has its own delegation mechanism, fully separate from Gmail inbox delegation: an account grants another user in the same domain access to its personal contact list. The delegate gets a Delegated contacts section at contacts.google.com and can view, add and edit the delegator's contacts there.

Because it is account-to-account and independent of mail flow, it can be layered on top of every option in this study:

  • Companion to option 2. Inbox delegation grants mail only — delegates cannot open or edit the mailbox's address book. Delegating the mailbox's contacts to the same team members closes that gap.
  • Bolt-on for options 3, 4 and 6. These have no shared address book at all: designate one account as the team's contact hub (an existing member's account or a dedicated one) and delegate its contacts to the others.

Limits to know before relying on it

  • Web-only for delegates — delegated contacts are not exposed in the Google Contacts mobile app; management happens at contacts.google.com.
  • No autocomplete feed — delegated contacts are searchable inside their section in Google Contacts but do not flow into the delegate's Gmail To-field suggestions; they fix maintenance and lookup, not typing speed.
  • All-or-nothing — the whole list is shared, with no per-label scoping.
  • Same domain only, and an admin must first enable contact sharing (Admin console → Directory → Directory settings → Sharing settings → Contact sharing).
  • Provisionable by API — the Contact Delegation API lets admins create, list and delete delegations at scale (see Topic 10 — API & Automation).

Third-party "shared contacts" tools — policy check

A market of add-ons (e.g. Shared Contacts for Gmail-type tools) exists precisely because of the native gap: label-based contact sharing between users. Per the standing nonprofit policy, these are excluded by default (recurring per-user cost, additional vendor access to Directory data). Possible exception: a free tier or a genuinely decisive feature deployed to a small set of power users only. The delegated mailbox's built-in contact list plus contact delegation (option 2) covers most needs at zero cost.

User perspective

  • Autocomplete expectations. Users expect "type three letters, get the right person". Only Directory entries and the current account's own contacts deliver that — personal contacts of colleagues never autocomplete for you.
  • Delegation surprise. Two of them, actually: while composing in the delegated mailbox there is no recipient autocomplete at all (see the comparison table), and delegates cannot browse or edit the mailbox's own contact list — inbox delegation grants mail only. Both gaps are why the shared address book must be fed deliberately (admin, API, or contact delegation).
  • Mobile parity — delegated inbox. In the Gmail app, the delegated account is selected from the profile menu (marked "Delegated"); composing there has the same no-autocomplete restriction as the web. Which contacts do you see? Only your own account's — the mailbox's list is not surfaced anywhere in the app.
  • Mobile parity — shared and delegated contacts. Contacts sync to the phone's address book per signed-in account: the shared mailbox's contacts reach the device only if that account itself is added to the phone (which needs its password — the shared-account pattern, not delegation). Contact delegation is no help on mobile either: delegated contact lists are exposed only at contacts.google.com on the web, not in the mobile Contacts app. Practical fallback for on-call staff: keep the few critical external numbers in the domain Directory (autocompletes everywhere) or in their personal contacts.

Administrator perspective

Web console

Admins control: Directory visibility (on/off per OU), shared external contacts (add/edit/delete), and the contact-sharing toggle that unlocks contact delegation (per-user granting then happens in Google Contacts itself, not in the console). There is no console UI to push contacts into a mailbox's personal list.

API & automation

Three APIs matter: the Admin SDK Directory API (shared external contacts for the whole tenant), the People API for per-account personal contacts (people.connections, otherContacts), and the Contact Delegation API to create, list and delete contact delegations programmatically (requires the Contacts admin privilege; same-domain pairs only). With domain-wide delegation, a script can also maintain a delegated mailbox's contact list from a source of truth (e.g. a Sheet or CRM export). Details in Topic 10 — API & Automation.
