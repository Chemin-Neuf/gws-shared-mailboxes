Topic 9 — Admin Controls & Governance

What can an administrator actually see and change from the Admin console web UI: membership, permissions, audit logs, delegation oversight — per option.

Comparison of admin controls and governance across the 7 options

Option Membership / Access Management Audit Trail Available to Admin License Cost Key Governance Caveats
1. Shared Password Account None — access is whoever knows the password. Login audit only all actions under one identity 1 license Admin cannot even enumerate who has access. Unmanageable by design.
2. Gmail Delegation Account Delegate list visible per user; grants manageable by users or via API; 25-delegate practical / 1,000 hard limit, 40 concurrent. Strong Gmail log search + audit events attribute actions to the delegate 1 license counts toward the user cap Console visibility of "who delegates what" tenant-wide is limited — API reporting recommended.
3. Collaborative Inbox Full roles (owner/manager/member), join policy, posting permissions per role Strong Groups audit log (membership, settings); content moderation history in group Free Assignment/status activity is not in any admin audit view — UI-only.
4. Distribution List Full same Groups admin surface as option 3 Good membership and settings audited; delivery is per-member Free No visibility into what members do with delivered copies.
5. Email Alias / Redirection Alias on a user (up to 30/user) or routing rule — centrally managed. Low routing changes audited; mail flow visible in log search Free Simple, but the recipient owns the entire mailbox lifecycle.
6. "Send Mail As" Config User-level configured in each member's Gmail settings; no console management Low Free Without API provisioning, admin has zero visibility of who may send as the shared address.
7. Email-to-Google Chat Space Space membership managed in Chat; app/webhook config in console. Partial Chat audit events in console Free The inbound email webhook/app is the fragile piece — ownership must be documented.

The governance gap nobody expects: "Send Mail As"

The one option users set up themselves (6) is the one with the least admin visibility. If your governance requires knowing "who is allowed to send as info@our-ngo.org", either provision sendAs centrally via API (Topic 10) or prefer mailbox-based options where the answer is structural (2) or role-based (3).

Where things live in the Admin console

Task Console Location
Create / configure a group (Collaborative Inbox or list) Directory → Groups → group → Access settings (also groups.google.com for managers)
Review delegates of a mailbox Directory → Users → user → Security / Gmail settings (limited); full inventory via API
Set delegation Sent-folder behavior Apps → Google Workspace → Gmail → User settings → Mail delegation
Routing / alias redirection rules Apps → Google Workspace → Gmail → Routing; or user → Add alternate email
Gmail log search (delivery trace) Reporting → Email log search
Groups audit events Reporting → Audit and investigation → Groups log events
Shared external contacts Directory → Directory settings → Shared external contacts (see Topic 7)
Delegate admin tasks without full super admin (least privilege) Account → Admin roles (pre-built or custom roles, e.g. Groups Administrator)

Audit evidence expires — retention on this edition

Every audit source cited above has a fixed retention window set by Google; administrators can neither extend nor shorten it (Google Workspace Admin Help, Data retention and lag times, checked 2026-09-16):

Audit source Retention (fixed by Google)
Email log search 30 days
Gmail, Groups, Chat, Admin, SAML and User log events 6 months

As with message content (Topic 5), evidence retention is architectural, not policy-driven: there is no Google Vault on this edition (no holds, no extended retention) and BigQuery log export is an Enterprise-tier feature — not available here. If governance requires evidence older than 6 months, the only native mitigation is a scheduled export via the Admin SDK Reports API (free, scriptable — see Topic 10).
